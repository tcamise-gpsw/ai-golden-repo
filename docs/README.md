# Hello World Documentation

How this application's documentation is organized, and the rules for keeping it honest.

## Conventions

1. **Docs are first-class.** A change is not done until the docs that describe it are
   current. Code and documentation ship together.

2. **Earn your words.** Every sentence must be concise and valuable. Do not add
   documentation for the sake of having documentation — a missing doc is better than a
   wrong or weightless one.

3. **Avoid rot-prone content.** Do not write anything that will silently become false:
   - No counts of things in code (routes, components, tests, fields — wrong the moment
     anything is added or removed).
   - No exhaustive lists of every X that currently exists. Describe the pattern; link to
     the source.
   - No copy-pasted signatures or types. Python docstrings and JSDoc are the per-symbol
     API references.

4. **Diagrams are code.** Use Mermaid fenced blocks. House style is `flowchart` /
   `sequenceDiagram` with `subgraph` boundaries (C4 discipline; renders on GitHub and in
   terminals).

5. **One source of truth per fact.** Link across docs instead of restating.

6. **Use real links.** Cross-references to other docs must be markdown links, not bare
   paths in backticks. A link is navigable; a path is not.

7. **Living docs move with the code.** If a PR changes structure, it updates
   [architecture/](architecture/) (and adds an ADR when the decision warrants one) in the
   same change.

Two categories matter:

- **Living docs** ([architecture/](architecture/), [adr/](adr/), top-level [docs/](./)
  files, and root [README.md](../README.md)/[README-project.md](../README-project.md)/[AGENTS.md](../AGENTS.md)) describe the
  system *as it is now* and are kept in sync with the code.
- **Point-in-time docs** ([plans/](plans/)) capture a change effort *as it was planned*.
  They are not updated after the work ships — their durable content folds into the living
  docs and ADRs.

There is no guides directory. API usage is in Python docstrings and JSDoc; end-user
usage is the root [README-project.md](../README-project.md); contributor mechanics are in
[AGENTS.md](../AGENTS.md); and how to extend a component lives next to it in
[architecture/](architecture/). Do not create a parallel prose layer that duplicates
these.

## API reference

The canonical HTTP API specification is [docs/specs/openapi.json](specs/openapi.json), generated
from the FastAPI route definitions and Pydantic models. Regenerate it with `make openapi`
whenever routes or the `Greeting` model change. Python function documentation lives as
docstrings in [backend/app/](../backend/app/); JavaScript component documentation lives as
JSDoc in [frontend/src/](../frontend/src/).

## `architecture/` — the living structure

The architecture docs are **numbered by recommended reading order**. The first two follow
the [C4 model](https://c4model.com) (a top-down zoom from the whole system inward); below
that, the numbered docs cover the application's internal layers, since strict C4 component
diagrams add little for a codebase this size.

| File | Level | Scope |
|---|---|---|
| [01-system-context.md](architecture/01-system-context.md) | C4 L1 — System Context | App as one box; its users |
| [02-containers.md](architecture/02-containers.md) | C4 L2 — Containers | Backend, frontend, nginx |
| [03-api.md](architecture/03-api.md) | API layer | REST contract and Greeting data model |
| [04-frontend.md](architecture/04-frontend.md) | Frontend | Component tree and data flow |

Rules:

- **Numbering is recommended reading order.** Later docs assume the vocabulary of earlier
  ones. This is distinct from ADR numbering, which is chronological identity.
- **There is no code-level (C4 L4) doc** — per-symbol detail belongs in Python docstrings
  and JSDoc.
- **Do not hand-model what tools generate** — wire formats, schemas, and APIs are linked,
  not duplicated (the canonical HTTP specification is [docs/specs/openapi.json](specs/openapi.json)).
- **"Extending" recipes belong here**, next to the structure they modify, not in a
  separate guide.

## `adr/` — Architecture Decision Records

ADRs record architecturally significant, hard-to-reverse decisions and the reasoning behind
them. They are append-only and immutable — a superseding ADR replaces an old decision rather
than editing it. See [adr/README.md](adr/README.md) for when to write one, the numbering and
status rules, and the template. Link ADRs to the relevant [architecture/](architecture/)
page so the decision and the current structure remain connected.

## `plans/` — historical design records

Future and active work are tracked in [GitHub Issues](https://github.com/tcamise-gpsw/ai-golden-repo/issues).
A plan captures the design and implementation details for an accepted change effort; each
numbered plan lives in its own directory:

```text
plans/NNN-<name>/
  design.md   — what and why
  plan.md     — tasks and sequencing
  notes.md    — append-only findings during the work
```

There are no active plans currently.

Lifecycle:

```text
issue  →  plan (when needed)  →  implement  →  fold durable content into
architecture/ (structure) and adr/ (decisions)  →  plan becomes historical
```

Plans are **not** kept in sync with the code after they ship. Treat a merged plan as a record
of *how we got here*, not *how it works now* — the living docs are the source of truth for the
latter.

## Where does X go?

| You're documenting… | Put it in… |
|---|---|
| How a user installs/runs the app | root [README-project.md](../README-project.md) |
| How to build, test, or commit | [AGENTS.md](../AGENTS.md) |
| How the system is structured / why | [docs/architecture/](architecture/) |
| A significant, hard-to-reverse decision | [docs/adr/](adr/) |
| A Python function's behavior | docstring on the function |
| A React component's props/behavior | JSDoc on the component |
| The HTTP API contract | [docs/specs/openapi.json](specs/openapi.json) (via `make openapi`) |
| Work that has not shipped | [GitHub Issues](https://github.com/tcamise-gpsw/ai-golden-repo/issues) (and a [plan record](plans/) when design warrants one) |
| How to extend a component | the relevant [docs/architecture/](architecture/) page |
